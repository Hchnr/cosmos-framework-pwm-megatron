## 1. 目标与已确认决策

在当前仓库内新增真正的 Megatron 模型并行训练路径，使用 Megatron-Core 的 `ColumnParallelLinear` / `RowParallelLinear` 切分矩阵计算，使用其 pipeline schedule 执行跨 stage 前反向，并支持 TP、PP、DP 组合。当前 Megatron-FSDP 后端保留为对照。

本版本已与用户确认：

1. 聚焦原始 **58-source、State128、36 层 Nano + width_only_1b Action 三塔**。
2. 保持原始全局训练 batch，通过调整梯度累积适应 TP/PP，不能以减小每次更新的数据量获得性能收益。
3. 先使用现有 **4 张 H100**，以 **TP=2 / PP=2 / DP=1** 验收组合路径。192 卡实测是后续验收项，不作为当前完成条件。
4. 继续保留 checkpoint 的旧归一化，恢复模型、FP32 master weights、Adam 状态、scheduler、trainer/RNG；不接受以重置优化器替代完整续训。
5. 本轮只编写和讨论计划，不修改训练实现，不启动正式训练。

## 3. 目标架构与代码组织


### 3.1 DP 后端的初始选择

建议 TP/PP 主路径先采用 **Megatron DDP + Megatron distributed optimizer**，按真正的 DP group 聚合梯度与分摊优化器状态。四卡 TP2/PP2 时 DP=1，没有 DP 分片收益，但仍走同一接口；四卡 TP2/PP1/DP2 必须额外覆盖真实 DP 通信。

不默认将现有 FSDP runtime 套在 TP/PP 模型外：现有实现使用全 WORLD mesh 和固定 tp=1，不能直接叠加。TP/PP + FSDP/HSDP 的混合组合如有显存收益，应作为后续明确设计项。distributed optimizer 也不能直接称为当前 ZeRO-3。

## 4. 全局 batch、数据与并行布局

### 4.1 以“逻辑 packed 微批槽位”定义原始更新

原始 192 卡、GA=3、CP=1，没有 TP/PP，因此一次 optimizer update 包含：

`192 个数据副本 × 3 个微批 = 576 个逻辑 packed 微批槽位`。

每个槽位包含多少样本、多少有效 token 会随 packing 改变。**576 不是 576 个样本，也不能直接套用固定 sample batch size。** 应同时记录实际样本数、有效视频/动作/文本 token 数和各源比例。

在每个 DP 副本仍消费同等容量的 packed 微批时：

`WORLD = TP × PP × DP`（本版本 CP=EP=1）
`M = 576 / DP`（M 为每次更新、每个 DP 副本的 pipeline microbatch 数）

| 场景 | WORLD | TP | PP | DP | 正式 M | 用途 |
| --- | ---: | ---: | ---: | ---: | ---: | --- |
| 原始生产基线 | 192 | 1 | 1 | 192 | 3 | 原始训练语义 |
| 四卡原生/FSDP 参考 | 4 | 1 | 1 | 4 | 144 | 四卡同 batch 性能参考 |
| 四卡 TP | 4 | 2 | 1 | 2 | 288 | TP + DP 通信 |
| 四卡 PP | 4 | 1 | 2 | 2 | 288 | PP + DP 通信 |
| 四卡 TP+PP | 4 | 2 | 2 | 1 | 576 | 当前主要组合验收 |
| 后续 192 卡示例 | 192 | 4 | 4 | 12 | 48 | 待集群实测，非最终推荐布局 |

诊断用 12 槽位则分别对应四卡参考 M=3、TP2/DP2 的 M=6、TP2/PP2 的 M=12，仅检查较短窗口；不能作为保持原始 batch 的正式结论。

原 TOML 的 `grad_accum_iter=3` 不能与 MCore schedule 的 M 重复累积。新 driver 每次调用代表一次完整 optimizer update，schedule 内部管理 M 个微批，完成后只 step 一次 optimizer 和 scheduler。

### 4.2 数据身份、分组与 RNG

1. 定义逻辑槽位 `(optimizer_update, original_micro_step, logical_data_rank)`，与当前 TP/PP/物理 rank 解耦。
2. 一个 DP 副本负责若干逻辑槽位；TP/PP ranks 不独立推进各自 loader，也不重复将数据副本数量乘以 TP 或 PP。
3. packing、增强、噪声和时间步必须有可复现身份。严格对照使用同一份已准备 batch 回放，避免把 RNG 差异误判为 TP 误差。
4. 按已确认的严格连续性要求，建立原 192 个逻辑流及其 RNG 的状态映射与虚拟化；按需推进而非启动 192 份大 worker pool。实际读取/解码使用有界 worker 池。
5. 区分两种边界：原始 52→58 源扩展本身按原实现执行 extend reset；TP/PP 迁移不能再额外重置。若从该源构建 58-source 参考，新旧 backend 使用同一份扩展后初始状态。
6. 不能声称任意跨拓扑 RNG 可“自动精确恢复”。先盘点 checkpoint 是否保存所需全部 rank/worker RNG；缺失时提出可实现的状态迁移边界，与用户确认，不能静默重采样。
7. dropout、TP 模型并行 RNG 与数据增强/扩散噪声 RNG 分离。重计算保存/恢复正确的 RNG，seed 不随流水线执行时序漂移。

### 4.3 数据 owner 与准备位置

每条 pipeline 的首 stage 上，由一个 TP owner 推进 loader，完成非可微数据准备，向同 stage TP ranks 广播必要 tensor。VAE 冻结编码优先只在 owner 执行，避免 TP 倍数重复计算。

可训练的输入投影和 timestep embedding 在首 stage 的模型内执行，**不得在 no_grad 广播阶段把可训练计算 detach**。只读 packing/RoPE 元信息发送到需要的 stages；loss target/mask 只需首/末端及必要消费者，避免每层发送视频原始 payload。

metadata 使用显式 tensor schema、长度与 dtype，禁止逐微批在热路径广播大型 Python 对象。每个 stage 以 microbatch ID 管理缓存、引用计数与释放，支持同时在途的多个微批。

## 5. TP 模型改造

### 5.1 三塔形状及约束

原始 UND / VIDEO 主干：36 层、hidden=4096、Q heads=32、KV heads=8、head_dim=128、MLP intermediate=12288。`width_only_1b` Action：hidden=1280、Q heads=32、KV heads=8、head_dim=128、MLP intermediate=3840。

**Action hidden=1280，但 Q 投影输出为 32×128=4096，不能假设 hidden = heads×head_dim。** 不直接用统一 GPT TransformerConfig 重建三塔；模块必须接受各塔独立的输入宽度、attention 投影宽度和 MLP 宽度。

首轮支持 TP=1/2，四卡扩展 TP=4；设计预留 TP=8。每次构建检查 Q/KV heads、MLP 和实际切分维度的整除约束。TP>8 的 KV 复制/分组策略不纳入本版。

### 5.2 模块映射

以下轴均按 PyTorch weight `[out_features, in_features]` 描述，避免与数学公式行列命名混淆。

| 原模块 | 目标模块/布局 | 权重 TP 切片 | 输出与通信 |
| --- | --- | --- | --- |
| 各塔 `q_proj/k_proj/v_proj` | `ColumnParallelLinear`，先保持 Q/K/V 三组独立参数 | axis=0，按完整 head 连续切片 | 输出局部 Q/KV heads，`gather_output=false` |
| 各塔 attention `o_proj` | `RowParallelLinear` | axis=1 | `input_is_parallel=true`，reduce 局部结果后回到完整 hidden |
| 各塔 MLP `gate_proj/up_proj` | `ColumnParallelLinear` | axis=0 | 局部 intermediate，不在激活前 gather |
| 各塔 MLP `down_proj` | `RowParallelLinear` | axis=1 | 输出完整 hidden，保持 residual 语义 |
| RMSNorm / 每 head QK norm | 小参数复制，按原轴计算 | 不切或按实际规范处理 | 标记正确的 TP 梯度合并/去重策略 |
| Vocab embedding / text head | 优先 `VocabParallelEmbedding`；CE 活跃时配套 vocab-parallel loss | vocab axis | 按实际激活路径决定，不引入全 vocab logits gather |
| VAE/Action 输入输出 head、domain affine | 首轮保留小模块复制或明确列/行组合 | 逐模块登记 | 复制模块的梯度不能重复求和；后续再 profile |

Column/Row 的返回值按 MCore `(output, bias)` 接口适配；不得将 tuple 当 tensor 传给原层。保留 bias、激活函数、RMSNorm eps、dtype 转换、weight decay、学习率倍数和冻结规则。

原 recipe 冻结 UND 等参数，并按名称选择生成/动作参数。不能因为更换模块名使冻结或 LR 分组失效，也不能把“三塔参与前向”误解为“三塔参数全部训练”。

### 5.3 跨塔 Attention 与梯度

- 同一个 TP rank 在三塔中拥有对应 head 范围；VIDEO 与 ACTION 所需的 UND / VIDEO / ACTION KV 在本 rank 拼接并计算，无需每层 gather 所有 heads。
- 保留原始同时、双向 KV 交互，不把三塔改为串行三个独立 Transformer。
- 保留 GQA 的 Q/KV 分组、原始 MRoPE、样本 mask、跨塔可见性、padding 规则和 stop-gradient / frozen UND 行为。
- `width_only_1b` 的 KV head 布局与主干匹配，可直接走本地 head 交互；其他需要 AxisAdapter 的 preset 不列入本版。
- 审查 QKV 三个 Column 分支对共享输入的 dgrad：保证各分支梯度相加并正确 TP 归约，不能漏加或重复归约。
- 复制的小模块和 norm 参数逐项标记：哪些梯度已完整、哪些只是 head-local 部分和。不要对所有 replicated 参数无差别再 all-reduce。
- 冻结参数仍可能处于需要传播输入梯度的路径；不能对所有 frozen-weight 计算统一 `no_grad()`。

### 5.4 初始化与存储

只构造本 stage 层和本 TP shard，优先 meta + 分片加载；不得每卡先加载完整 36 层和完整 optimizer 再切片。保存 canonical 全局形状、TP 轴、偏移和 PP 全局层号，转换前后检查参数元素覆盖与重复持有情况。

先分离 Q/K/V 和 gate/up，完成基线映射后再考虑融合。若未来融合，必须定义逐组切片顺序，不能将拼接后的 QKV 矩阵简单均分导致各 rank head 对应错位。

## 6. PP stage 与流水线调度

### 6.1 沿深度切分，每层仍包含三塔

PP=2 的初始布局：

```text
数据 / 冻结 VAE → 输入模块 → [三塔 layers 0..17]
                              │ U / V / A 激活 + 微批 metadata
                              ▼
                         [三塔 layers 18..35] → 输出 heads → 原 loss
```

每个 TP rank 只拥有本 stage 的对应 TP shard。PP=4 可从每 stage 9 层开始，但最终应结合首端 VAE/packing、末端 heads/loss 的开销，按测量调整边界，不能按层数均分就认定负载均衡。

首 stage 拥有 embedding、输入投影和输入侧可训练 conditioning；末 stage 拥有最终 norm、视频/动作输出 head 与 loss。需要跨多 stage 使用的可训练 conditioning，必须明确其激活及梯度传递，不能在各 stage 各建一份不同权重。

构建 `stage_parameter_manifest`，记录每个 canonical 参数的唯一 owner、TP 切片、共享关系、可训练性。对重复或未分配参数直接报错。共享 embedding/head 按真实配置处理，不强制将原本不 tied 的参数绑在一起。

### 6.2 传输契约：先兼容 MCore 的单输出反向接口

原 SequencePack 为包含张量和元数据的 dict，不能直接作为 P2P payload。安装版本的标准 schedule 的 `backward_step` 主要沿单个输出 tensor 反传，不能仅因为 P2P 支持 tensor list 就假定能直接传三个独立流。

建议首轮方案：

1. 将可微 U/V/A 激活打包为 **一个连续 tensor**；记录三个切片的 shape/offset，接收端以 view 恢复。
2. 不将 Action 激活填充到 4096 宽度；使用真实 1280 宽度打包。打包/解包必须保留 autograd，不能经 CPU、`detach()` 或不可微拷贝断链。
3. 初期使用明确的固定最大传输布局，short UND 桶通过有效长度区分；后续再做按桶 shape 协议。额外 padding 仅用于传输，不改变真实 attention 和 loss。
4. 通过非交错 schedule 的 `adjust_tensor_shapes_fn` / 对应通信接口声明真实 payload shape；先验证任意 shape、dtype、反向梯度与输出释放选项兼容，不依赖 GPT 的默认 `[S,B,H]` 推导。
5. 只读 metadata 与可微 payload 分开：sample IDs、长度、RoPE 位置、任务标签、桶类型、valid mask 按需广播；Flex BlockMask 在各 stage 本地重建并按微批复用，不 pickle 内核对象。
6. 冻结 UND 原本不需要输入梯度时，在接收端恢复对应 stop-gradient 语义，防止单个可微 payload 使整条冻结 UND 图意外参与反向；对未来需要梯度的情形不得误 detach。
7. 缓存 key 使用更新号与微批号，不用“当前全局 batch”可变对象；1F1B 的多个在途微批各自持有正确 metadata。

**必须先做两层、异宽度 U/V/A、非零梯度的 P2P 原型。** 若上述方案与 MCore API 不兼容，再评估 MultiModulePipelineCommunicator 或窄范围 schedule adapter；不能在没有验证的情况下重写一套全量 pipeline engine。

原始 TOML 的 `fixed_gen_tokens=62592` 包含 Action 容量；小三塔拆分后 VIDEO 容量为 `62592−2944=59648`。P0 应以实际运行张量确认，不混用配置 GEN 与物理 VIDEO 长度。以 U=11776、V=59648、A=2944，宽度 4096/4096/1280、BF16 估算，每个未做 SP 的边界 payload 约 **592.6 MB**，反向还有同量级梯度；pack/unpack 还占带宽和临时内存。

因此 PP 不保证四卡更快。先以此估算通信、激活驻留和 1F1B 峰值，不能假定 TP 自动将复制的 residual boundary 激活减为 1/TP。

### 6.3 调度与 optimizer-update 生命周期

- 使用 MCore `get_forward_backward_func()`，PP>1 首轮采用 **non-interleaved 1F1B**；PP=1 走其无 pipeline 路径。
- stage 实现 `set_input_tensor`、配置访问及 schedule 需要的生命周期接口；一次 driver 调用处理完整 M 个微批。
- 首轮禁止 VPP 和未经支持的 P2P overlap。安装版 non-interleaved schedule 明确不支持 `overlap_p2p_comm=true`，不能把所有 overlap 开关都打开。
- forward step 返回模型输出与 loss closure；末 stage 计算 loss，其他 stages 不伪造本地 loss.backward()。
- schedule 完成后 finalize grads → 检查有限性 → 全模型梯度裁剪 → optimizer step → scheduler step → zero grad。跳过更新状态在所有 TP/PP/DP rank 同步。
- callbacks 区分“微批事件”和“完整更新事件”，checkpoint/save_iter/scheduler/日志 step 都以 optimizer update 为单位。
- pipeline warmup/drain、微批耗尽、媒体跳过、异常停止必须按统一协议结束，避免某 stage 等不到对端。

## 7. Loss、梯度归约与原目标保持

这部分应先于性能优化完成。

### 7.1 明确 group 职责

| group | 用途 | 不能做的事情 |
| --- | --- | --- |
| TP | 局部矩阵结果、input gradient、需要求和的复制参数梯度 | 不能把同一微批在不同 TP rank 的 loss 当不同样本 |
| PP | 激活/梯度 P2P、必要的共享参数与状态协调 | 不能要求每个 stage 都执行末 stage 的 loss collective |
| DP | 独立数据副本的梯度与样本统计聚合 | 不能继续使用 WORLD 代替 |
| 全局控制 | 有限性、失败、停止、checkpoint 协调 | 只在所有 rank 约定的生命周期位置调用 |

现有 `_loss_averaging_group()` 在原 FSDP 情形返回 WORLD；新路径必须注入真正的 DP group。审查 `_sample_level_loss_scale`、梯度统计、clip、日志、loader 分片、分布式异常检测和 DCP 中的 WORLD 假设。

### 7.2 避免 loss 多除或少除 M/DP

原 trainer 显式 `loss / GA`，MCore schedule 也有按 `num_microbatches` 缩放的逻辑。新 driver 只能有一个负责累积平均的入口，不得把原 scaled loss 再除一次 M。

原目标包含样本数、动作有效 mask、时间步权重和各模态 loss weight；不能擅自改成全 token CE 或统一全 token 平均。采用原 loss 公式，显式设置 MCore token-normalization 行为；sample-averaged flow loss 不冒充 token loss。

**保持 576 个槽位只是必要条件。** 若原来按同一个 old micro-step 的 192 个 rank 汇总样本数，而现在把它们分到更多 pipeline 微批，直接对新微批各自求平均会改变目标。实现应：

1. 在更新准备阶段按原逻辑 micro-step 汇总样本数/模态计数，记录每个槽位的原始权重。
2. 映射到新 DP/M 排列后，计算显式修正系数，补偿新 DP averaging 与 schedule 的 `1/M`。
3. 样本均衡时退化为普通平均；样本数不同、混合模态、全 mask 或缺少 Action 时，依然与原基线梯度等价。
4. loss collective 在所有末 stage DP ranks 相同顺序执行；不能因某个微批缺少模态跳过 collective。

### 7.3 全局梯度裁剪

使用 MCore finalize/optimizer 的梯度同步和 norm 机制，审计 canonical 参数是否被 TP 复制、DP 分片或 PP 唯一持有。全模型 norm 必须覆盖所有 PP stages、去重 TP replicas，并避免重复计算 DP 副本。不直接复用现有 FSDP 的“只在 shard group 求一次范数”实现。

先在 FP32 下比较 clipping 前梯度、norm、裁剪系数和更新后权重；仅比较各 stage 局部 norm 不能证明全模型裁剪正确。

## 8. 完整 checkpoint 迁移与恢复

### 8.1 需要保留的状态

| 类别 | 迁移要求 |
| --- | --- |
| 模型 | 所有可训练/冻结参数、buffer、归一化契约、全局层身份 |
| FP32 master weights | 从实际优化器 master 状态迁移，不能以 BF16 权重转 FP32 伪造 |
| Adam | 每参数 `exp_avg`、`exp_avg_sq`、step、参数组超参及实现所需字段 |
| Scheduler / trainer | 当前迭代、学习率位置、累计计数、跳过更新状态 |
| 数据 / RNG | 逻辑流游标、worker 执行状态、数据 RNG、各随机源的映射 |
| 格式元数据 | 格式版本、原始契约、TP/PP/DP 拓扑、参数布局与来源标识 |

checkpoint 内的“106 个旧域归一化”指动作数据的逐域、逐维 affine：`x_normalized = x * scale + bias`，由 mask 选择应用维度；不是 LayerNorm/RMSNorm，也不是 106 个数据集。保留它们才能保持原模型训练时的动作尺度。State128 使用独立的配套旧统计；新增域按现有扩展契约追加，模型和 loader 使用同一份配置。

### 8.2 参数映射与转换工具

拟新增 `tools/convert_cosmos_checkpoint_to_megatron_tp_pp.py`：

1. 读取原始 DCP metadata、契约和 optimizer 参数身份；检查 `.save_complete` 与各组件完整性。
2. 按 canonical FQN 建表，再确定目标 PP stage、stage-local 名称、TP 轴/offset、复制或共享关系。
3. 列并行权重沿 axis=0 切，行并行沿 axis=1 切；Adam moments 使用同一变换；scalar step 不切。
4. 分别映射模型计算权重、FP32 master 和 moments，不能假定它们 dtype、存储布局和键名相同。
5. 按块读取/写入，限制 CPU/GPU 内存；不在每个目标 rank 上完整物化全部源模型与优化器。
6. 输出版本化的新 checkpoint 与转换 manifest，记录精确覆盖情况、未映射项、共享项和校验摘要。任何丢失、非预期重复或不兼容超参都失败退出。
7. 先做单 tensor / 单层重建，再做全模型 shard→canonical 重建；比对原始状态，不仅检查 shape。

源 checkpoint 只读。不得覆盖旧作业输出目录或修改原数据。转换结果写入独立输出树；在所有组件完成后才发布完成标记。

### 8.3 优化器的语义桥接

从 Cosmos FusedAdam 迁移到 MCore optimizer 不是只换 key。显式核对 betas、epsilon、weight decay 是否 decoupled、bias correction、step 计数、参数组 LR 倍数、FP32 accumulation/master 策略和冻结参数选择。

先用已知 FP32 权重、非零 moments、非零 step 的单次更新测试两者公式；有差异时先找可兼容配置或实现局部状态适配。不能用“优化器不同”解释大误差后继续宣称完整续训通过。

### 8.4 新布局 checkpoint 与 restart

优先使用 MCore 模型/optimizer 的 sharded state 表示及 distributed checkpoint 能力，外层接入 Cosmos 的调度与保存目录协议。第一版先跑通**同步、完整、可校验**保存/恢复，再恢复异步写入；未支持的异步开关必须报错或显式关闭，不能悄悄只保存模型。

必测：原 DCP → TP2/PP2 → 至少一次更新 → 新 checkpoint → 全进程退出 → 新进程恢复 → 继续更新，与不中断的新路径对照。逐项检查模型、master、moments、scheduler、迭代和下一批样本/噪声。

同拓扑完整恢复是本版必需。模型状态的 topology-independent canonical 映射也必须清楚；跨 TP/PP/DP 拓扑的优化器和 loader 再分布需单独测试，未验收前不能宣称任意拓扑恢复。

## 9. 原有优化的继承与新路径优化顺序

| 项目 | 首轮正确性阶段 | 完整容量验收阶段 |
| --- | --- | --- |
| Attention | 小容量 FP32 math 参考；先验证局部 heads 与 mask | VIDEO FA3，UND/ACTION Flex，保持原可见性 |
| torch.compile | 先 eager 定位误差 | 恢复逐 block 编译；显式检查 MCore autograd/通信边界兼容 |
| Activation checkpointing | 先关闭，再单独启用 | 恢复逐 block full AC，验证 TP RNG 与 PP 在途微批 |
| Packing | 固定真实多样本回放，不能只测单样本无 padding | 原顺序 packing、固定容量和 short UND 桶 |
| BF16 / FP32 master | FP32 数学对照先通过 | BF16 计算，FP32 master/moments 和规定的累积/通信精度 |
| DP overlap | 初期关闭便于定位 | correctness 通过后开启梯度/参数通信重叠 |
| TP Sequence Parallel | 首轮关闭，保留全 hidden residual | 作为后续可选优化；若完整容量不 fit，则提升为必须讨论项 |
| TP 通信融合 / TE | 先使用原生 MCore Column/Row，避免多变量 | profile 后选择；不以替换所有原 attention 内核为前提 |
| PP overlap / VPP | 不启用 | 本版本不作为必需，后续单独评估 |
| Loader / metadata cache / staging | 保留并改为 DP/逻辑流 owner | 避免每 TP rank 重复解码、增加无界主机内存 |
| Async checkpoint / VAE compile | 不计入首轮数学对照 | 分别恢复并测量稳态、首次编译和保存开销 |

Sequence Parallel 与 CP 不同：前者通常依附 TP，减少部分复制的 residual/norm 激活；不能把它当成已经解决三塔长序列 CP。若启用 SP，需重新设计三种序列长度的切分、TP gather/scatter、PP payload、mask、复制 norm 梯度和 checkpoint RNG，完成独立验收。

新增 TP/PP 路径若暂时无法 compile 或丢失 FA3，不可直接标记性能完成；应先记录差异与瓶颈，再决定修复或讨论版本范围。不能将 FP32 小容量/eager 的通过直接替代生产 BF16 + compile + AC + packing 通过。

## 10. 训练配置与启动接口（拟议）

保留原训练主入口 `python -m cosmos_framework.scripts.train --sft-toml=...`，按 backend 选择专门的模型并行 driver。新增独立 recipe，避免把原 FSDP recipe 原地改成另一种含义：

- `examples/toml/sft_config/action128_pretrain_state_h1_58src_megatron_tp_pp.toml`
- `examples/launch_pretrain_state_h1_58src_megatron_tp_pp.sh`
- 继续引用原始数据路径、配比、归一化策略及优化器/训练超参。

配置设计示例（实现后才能运行）：

```toml

[model.parallelism.megatron]

pipeline_model_parallel_size = 2

[trainer.megatron]
```

DP 自动由 `WORLD/(TP*PP)` 推导；不能继续用旧 shard16/replica12 推导 WORLD。schema 对新 backend 拒绝不兼容的 HSDP/CP/PP 设置，原路径不变；最终字段名称在实现前一次性定稿。

启动器应显式输出 TP/PP/DP group membership、stage 层范围、每卡参数量、实际 M、逻辑 batch 大小和加载状态摘要。四卡默认 TP2/PP2，新的输出目录、转换后 checkpoint 路径与现有 FSDP 作业隔离。

## 11. 实施里程碑

按依赖顺序推进；某阶段数学或状态验证失败，先修复，不提前叠加性能优化。

| 阶段 | 工作内容 | 交付与退出条件 |
| --- | --- | --- |
| P0：接口与状态盘点 | 展开实际模型/optimizer 配置；列出冻结参数、规范 FQN、实际 token shape、loss 分母、RNG/loader 保存范围；锁定 MCore API | 参数/状态 manifest、同 batch replay schema、确认无未说明的迁移缺口 |
| P1：TP/PP 机制原型 | 原生 Column/Row 单层；异宽度 payload；两层 PP；DP groups 和 loss 权重原型 | 非零前向/梯度通过，真实权重/计算切分，P2P 梯度双向正确 |
| P2：三塔 TP | 完成局部 Q/KV、GQA、RoPE、跨塔 KV、三塔 MLP/norm、冻结与 LR 分组 | TP1/2/4 与原数学 FP32 对照；含 padding、缺少 Action、非均衡样本 |
| P3：PP 与 driver | stage-local 构建、首末端所有权、1F1B、更新级 callbacks/clip/step | TP1/PP2 和 TP2/PP2 的 12 槽位多更新对照；每个 stage 只拥有所属层 |
| P4：完整状态迁移 | 原 DCP 转换、FP32 masters/moments、scheduler、规范状态保存与恢复 | 源状态逐项重建；迁移后第一步更新与参考一致；保存退出恢复成功 |
| P5：严格数据连续性 | 192 逻辑流虚拟化、RNG 映射、同一 576 槽位/样本/噪声 | 每次更新槽位身份、样本、增强和噪声对齐；不重复消费 TP/PP 副本 |
| P6：生产计算设置 | 恢复 FA3/Flex、compile、full AC、原 packing/short UND、生产 loader | 四卡原始容量可运行、无 NaN/OOM；各项优化实际生效 |
| P7：四卡完整验收 | 完整 576 槽位，完整续训、checkpoint restart、性能画像 | 满足第 12 节四卡门槛；记录性能，但不以四卡收益作为阻塞门槛 |
| P8：后续 192 卡 | 节点拓扑、TP/PP/DP 组合搜索、同 batch 稳态比较 | 独立性能验收；当前四卡交付不宣称完成此项 |

P2 和 P3 可先从合成数据原型推进；P4/P5 依赖 P0 的真实状态盘点。P6 不能以仅缩小 token 容量作为完成。当前计划不承诺日期，应在 P0/P1 量出 checkpoint I/O、微批时长和通信后估算工期。

## 12. 验收设计

### 12.1 四卡组合矩阵

| 组合 | 诊断 M（共 12 槽位） | 正式 M（共 576 槽位） | 主要检查 |
| --- | ---: | ---: | --- |
| 原 PyTorch FSDP，DP4 | 3 | 144 | 原始目标与当前可运行参考 |
| 新路径 TP1/PP1/DP4 | 3 | 144 | 新 driver/optimizer 桥接误差 |
| 新路径 TP2/PP1/DP2 | 6 | 288 | TP 与真实 DP 梯度通信 |
| 新路径 TP1/PP2/DP2 | 6 | 288 | PP 与真实 DP 梯度通信 |
| 新路径 TP2/PP2/DP1 | 12 | 576 | 必须通过的 TP+PP 组合 |
| 新路径 TP4/PP1/DP1 | 12 | 576 | KV heads 切分扩展；非首个里程碑阻塞项 |

不是每个矩阵点都要求立即跑同等长度的正式训练；先跑诊断矩阵，正式四卡必须覆盖原生参考、TP2/PP2，真实 DP 组合至少完成完整状态更新与重启检查。192 卡之后才可证明多节点模型并行性能。

### 12.2 数学与更新正确性

统一从同一份模型与 optimizer 状态开始，准备独立于执行拓扑的真实多样本回放。

- **FP32 基础门槛**：输入和 metadata 一致；无非有限；全部参数重建后梯度全局相对 L2 ≤ `1e-4`、余弦 ≥ `0.999999`。同时输出逐塔、逐层、逐参数误差，不能用大矩阵掩盖漏掉的小模块；理论零梯度使用绝对误差和显式零/非零检查。
- **状态更新门槛**：先验证非零 moments、非零 step 的单步 Adam；再比较完整模型裁剪前梯度、全模型 norm、裁剪系数、更新后 FP32 master 与 moments。权重/moments 对照以 `relative L2 ≤ 1e-4` 为初始上限，近零项另用绝对容差，门槛必须在运行前固定。
- **跨更新门槛**：至少 3 次连续更新，检查 scheduler、step、LR 参数组、冻结权重不变、可训练参数确实更新。不能只做从零 moments 开始的第一步。
- **BF16 生产门槛**：loss 轨迹相对差以 1% 为初始上限；重复运行先测原参考波动，超界先调查，不能事后修改门槛来通过。记录梯度/更新状态误差分布，FP32 为主要数学隔离检查，不沿用“所有 BF16 梯度始终低于 2%”的未经证明结论。
- 覆盖 FA3/Flex、compile 开关、full AC、packing 多样本、short/full UND 桶、不同有效 Action mask、空模态、非均衡 packed 样本数及输入投影 LR 倍数。
- 所有梯度比较必须在同一语义位置采集，例如 finalize 后、clip 前；不能将某端局部 shard 梯度和另一端全局平均梯度直接比较。

### 12.3 数据连续性与完整恢复门槛

- 每次更新恰好 576 个逻辑槽位，无丢失、无重复，映射到原始 192×3 的同一批数据。
- 对齐样本身份、packing 边界、增强参数、噪声/时间步内容及有效 mask，不只比较数据源名称或 seed。
- 旧动作和 State128 归一化一致；新增域契约和投影路由严格校验。
- 中断恢复后，至少再完成 2 个更新，与同拓扑不中断训练的下一批身份/噪声和状态一致。
- 源缺少连续性所需状态时，明确报告缺项并讨论修复，不以默认 seed 或 reset cursor 代替。

### 12.4 四卡性能记录与 192 卡性能门槛

**用户已确认：四卡先以正确性、完整续训和可运行性验收；性能收益留到 192 卡判断。** 四卡也必须测量并如实报告慢多少、原因在哪里，不能将其称为已实现性能收益。

四卡正式测量保持 576 槽位和原始容量，记录整次 update wall time、有效 token/s、样本/s、峰值显存/主机内存、TP collectives、PP P2P、DP reduce、VAE/packing 与 stage bubble。先采集短 profile 再决定稳定窗口；使用相同回放与稳态设置复测，避免一次首次编译比较。

192 卡后续阶段：基于节点 GPU/NVLink/网络拓扑选择 TP 尽量位于高速域、PP/DP 合理跨节点的布局；比较多个候选，而不是预设 TP4/PP4 最好。保持每次更新同一 576 槽位、相同目标函数及计算设置。

原始要求仍是有收益或基本持平、无显著劣化。建议后续预先固定“整次更新吞吐下降不超过 3%”为基本持平门槛，并要求重复窗口/交换运行顺序；正式 192 卡运行前再与用户确认。分别报告排除首次编译和 checkpoint 的稳态性能，以及包含真实保存开销的训练性能。

## 13. 主要风险与处理原则

| 风险 | 影响 | 处理与升级讨论条件 |
| --- | --- | --- |
| 三塔异构宽度与双向 KV | 不能直接换成通用 GPT block | 自定义三塔 block，TP Linear 作为真实矩阵并行基础，逐塔验证 |
| PP payload 接近 0.6 GB/边界/微批 | 通信和额外 buffer 抵消显存/速度收益 | 首先量化，避免宽度 padding；需要时评估 SP 或更好的边界协议 |
| 原 WORLD collective 假设 | 错误 loss、重复梯度或死锁 | P0 全局搜索归约点，按 group 职责逐个审计 |
| 原 batch 分组被重新排列 | 数量相同但优化目标改变 | 保留原逻辑 micro-step 的权重与样本统计，显式 loss 缩放 |
| 源 RNG/worker 状态不足 | 无法满足严格数据连续性 | P0 先验证状态可用；不足时暂停该承诺并讨论补采或可恢复基线，不能静默降级 |
| 用 MCore optimizer 导入 FusedAdam 状态 | step、epsilon、master 语义不同 | 单参数非零 moments 公式对照，再做完整迁移 |
| TP duplicate 参数的 norm/grad | 裁剪错误或梯度多乘 TP | canonical 参数身份与复制/分片标记；全模型 norm 对照 |
| 1F1B 多个在途微批 | metadata 被覆盖、batch 用错 | 按微批缓存与释放，显式身份检查和异常协议 |
| compile + full AC + MCore autograd | 图断裂、重计算 RNG 或权重错误 | eager→compile→AC 分层启用，保持生产优化验收项 |
| 576 微批更新的内存/准备压力 | 主机内存无界、恢复耗时较长 | 只预存轻量 manifest/计数，视频解码、VAE 和 GPU batch 按有界窗口流式推进 |
| DP-only 新路径在原始容量不 fit | 不能覆盖所有矩阵点的正式容量 | 诊断阶段缩小容量；原始容量必须覆盖 TP2/PP2 与当前可运行 FSDP 参考，不以 OOM 隐藏测试缺口 |
| 192 卡拓扑未知 | 无法选定最佳 TP/PP 排布 | 当前只给候选；资源就绪后测链路并配置 group rank 顺序 |

### 13.1 需要继续与用户讨论的触发条件

以下情况出现时，应先给出具体测量/缺口，再讨论方案，不自行削减目标：

- checkpoint 缺失逻辑数据连续性所需状态，严格恢复无法实现。
- 保留原始容量、compile、FA3/Flex 和 full AC 后四卡 TP2/PP2 仍 OOM，需要将 SP 或其他方案提升为本版必需项。
- 标准 MCore schedule 无法承载当前三塔 payload，需要窄范围扩展或更换流水线通信方案。
- optimizer 数学语义或 loss 定义不能在既定误差范围保持。
- 首末 stage 明显不均衡，需要改层边界、移动输入处理，或引入额外 encoder stage。
- 后续希望同时引入三塔 CP、FP8、VPP 或其他模型族，导致版本范围扩大。

常规实现细节、可逆修复和已批准范围内的验证不反复请求许可。与用户讨论的是目标/语义/验收边界的变化。

## 14. 最终交付与完成定义

四卡 v0.0.1 交付必须包括：

1. 实际使用 MCore Column/Row TP Linear 的三塔模块；TP2/PP2 stage-local 模型，非复制伪实现。
2. MCore 1F1B 调度和真正的 DP group 支持；无重复 GA/optimizer step/scheduler step。
3. 原始 DCP 完整状态转换工具、规范参数布局清单和版本化 checkpoint 格式。
4. 原始 58-source 的逻辑数据分片/RNG 映射；逐更新同一组样本与噪声。
5. 新训练 shell、TOML、明确的配置 schema 和独立输出目录。
6. 分层正确性检查、576 槽位完整续训与重启验收，恢复原生产 attention/compile/AC/packing 设置。
7. 四卡时间/显存/通信画像与限制说明；192 卡后续验收清单。
8. 一份简洁的中文实现说明，清楚列出“已支持/未支持、运行入口、布局、续训和结果”，避免堆积过程性流水账。

本计划完成只表示设计已写出并核对，不表示 TP/PP 已实现。本版实现完成时，应明确标注 **“四卡功能与完整续训验收通过，192 卡性能待验收”**；不得用当前 FSDP 的 +4.48% 代替新 TP/PP 路径的结果。
